> **Status**: In Review
> **Author**: Claude（起草，作者授权按 Claude 的节奏推进）
> **Last Updated**: 2026-10-17
> **Last Verified**: 2026-10-17

## Summary

守秘人笔记本上运行的一个 Node.js 中转程序：托管游戏页面，开房间、发凭据、按收件人投递消息、断线补发。
它不懂规则、不读消息内容；守秘人浏览器是唯一的权威（ADR-0001）。线下走热点 / 同一 Wi-Fi，线上走 Tailscale，同一套代码。

> **Quick reference** — Layer: `Foundation` · Priority: `MVP` · Key deps: `None`（被 16、17、27、28 依赖）

## Overview

真人守秘人辅助模式需要守秘人和几名玩家各用自己的设备参加同一局。现有游戏是纯前端单机程序，因此新增一个只做中转的服务程序：
守秘人在自己的笔记本上启动它，浏览器打开 `http://localhost:8080` 照常进入游戏（旧存档与 AI 密钥都在这个地址下）；
在大厅里点"开房间"，拿到给玩家的链接与邀请码；玩家在手机或电脑浏览器打开链接即可加入，不需要安装任何东西，也不需要信任证书。
服务程序不参与任何规则判断，它只认"谁是谁"和"发给谁"。

## Detailed Design

### Core Rules

**1. 启动与托管**
1. 启动命令 `npm start`（目录 `server/`，不放进 `src/`，避免被 Service Worker 预缓存）。启动时打印三档玩家地址与 Tailscale 地址（若有）。
2. 监听三个端口，提供同一份 `src/` 静态页面与同一个 WebSocket 入口 `/__relay/ws`：

   | 端口（默认） | 绑定 | 用途 |
   |---|---|---|
   | 8080 http | 仅 `127.0.0.1` | **守秘人专用**。与现有 `python -m http.server 8080` 同一个源，旧存档、密钥、模组列表照常可用 |
   | 8081 http | 所有网卡 | 玩家 C 档（普通 http），也是 `tailscale serve` 的上游 |
   | 8443 https | 所有网卡 | 玩家 A 档（mkcert 证书）/ B 档（自签证书） |

3. 证书：`server/.cert/` 下若有 mkcert 证书则用它（A 档）；否则首次启动用 `openssl` 生成自签证书（B 档）；没有 `openssl` 时不开 8443，
   只提供 C 档并打印一行说明。**证书只为保证能玩，从不因证书不受信任或没有 https 拒绝任何人加入**（作者决定）。
4. 静态托管必须带正确的 `Content-Type`（`.mjs` / `.js` → `text/javascript`，另有 `.css`、`.json`、`.svg`、`.png`、`.webp`、`.woff2` 等），
   否则浏览器拒绝加载 ES 模块、页面完全打不开（原型实测）。只读 `src/` 内的文件，拒绝 `..` 与符号链接越界。
5. `GET /__relay/info` **只对 `127.0.0.1` 应答**：返回玩家可用地址（本机非回环 IPv4、Tailscale 名称与 100.x 地址）、三档端口、证书档位。
   守秘人页面据此生成玩家链接——不能用页面自身的 `localhost` 地址（原型发现 6）。

**2. 房间与身份**
1. 只有从 8080（本机）连上的页面可以开房间。一台服务程序同时只有一个房间。
2. 开房间时生成：房间号（6 位，展示用）、**房间密钥**与**邀请码**（各 128 位随机值）。房间密钥只显示在守秘人页面，邀请码进玩家链接。
3. 凭房间密钥加入为 `developer`；凭邀请码加入为 `guest`。**开房间的本机页面就是守秘人**（`memberId: 'keeper'`）。
   守秘人断线期间，远程凭密钥加入的连接**不能顶替守秘人**；守秘人凭自己的成员令牌重连。
   守秘人浏览器丢了令牌（清除了浏览器数据）时，**只有从本机端口（8080）凭房间密钥加入**才能取回守秘人身份——坐在服务程序那台电脑前的人就是守秘人。
4. 加入成功后发给客户端一个**成员令牌**（128 位），客户端存在本机，用于重连；同一令牌的新连接顶替旧连接（同一人换了网络）。
5. 开发者账号可以：重新生成邀请码（旧码立即失效，已在房间的人不受影响）、移除成员（吊销其令牌并断开）、关闭房间。
6. **持久化**：房间号、密钥、邀请码与成员令牌的**哈希**写入 `server/data/room.json`。服务程序重启后房间与链接继续有效，固定团（系统 28）
   不必每次重发链接。只存哈希，文件泄露不能直接拿来加入。
7. 成员名单（`memberId`、显示名、角色、是否在线）以 `kind: 'system'` 消息广播给全员。

**3. 投递规则（服务程序只看信封，不读 `body`）**
信封格式见 ADR-0001（`v`、`room`、`epoch`、`from`、`to`、`kind`、`dseq`、`body`）。

| 规则 | 不符合时 |
|---|---|
| `from` 由服务程序按连接身份覆盖，客户端填写无效 | — |
| `state` / `event` 只接受守秘人连接发出 | 丢弃并记录 |
| `guest` 只能发 `request`，`to` 只能是 `'keeper'` | 丢弃并记录 |
| `to: 'all'` 只用于 `kind: 'system'` | 丢弃并记录 |
| 玩家之间不能直接发消息；出示线索、分享地图都以 `request` 发给守秘人浏览器 | 丢弃并记录 |
| 单条消息不超过上限（见 Formulas） | 丢弃，回给发送者一条 `system` 错误 |
| 守秘人不在线时，玩家的 `request` 不排队 | 回给发送者 `system: keeper_offline`，由玩家稍后重试 |

"丢弃并记录"只写服务程序的本地日志（不含 `body`），不通知其他人。

**4. 投递序号与断线补发**
1. 服务程序为每名收件人分配连续的 `dseq`，并为每人保留最近 N 条已投递消息（已过滤的那一份，原样保存，不读内容）。
2. 客户端重连时上报 `epoch` 与最后收到的 `dseq`（客户端必须把 `dseq` 存为持久状态，不能从收件箱推算——原型发现 5）：
   - `epoch` 相同且缓存覆盖缺口 → 直接补发；
   - `epoch` 不同（守秘人浏览器刷新过）或缓存不覆盖 → 服务程序向守秘人浏览器发 `system: snapshot_needed(memberId)`，由它生成该成员的快照。
3. 新成员加入同样触发 `snapshot_needed`。
4. 心跳：服务程序定期 ping；超时未应答的连接视为断线，成员标为离线（令牌保留）。

### States and Transitions

| 状态 | 进入条件 | 离开条件 | 行为 |
|---|---|---|---|
| 无房间 | 服务程序启动且无 `room.json`；或房间被关闭 | 守秘人在本机页面开房间 | 只托管页面；拒绝任何加入 |
| 等待守秘人 | 服务程序启动且有 `room.json`；或守秘人断线 | 守秘人凭令牌（或首次凭密钥）连上 | 玩家可加入、收补发；`request` 回 `keeper_offline` |
| 进行中 | 守秘人在线 | 守秘人断线 / 关闭房间 | 按投递规则转发 |
| 已关闭 | 开发者账号关闭房间 | — | 断开全部连接，删除 `room.json`，回到"无房间" |

成员状态：`在线` ⇄ `离线`（断线 / 心跳超时；凭令牌重连回到在线）；`已移除`（令牌吊销，不可恢复，需新邀请）。

### Interactions with Other Systems

| 系统 | 方向 | 接口 |
|---|---|---|
| 16 账号身份 | 15 提供 | 角色 `developer` / `guest`、`memberId`、成员令牌 |
| 17 多人状态同步 | 15 承载 | 信封、`dseq`、补发、`snapshot_needed`；17 定义 `body` |
| 18 按玩家过滤 | 无直接接口 | 过滤在守秘人浏览器完成（`projectFor`），服务程序只按 `to` 投递 |
| 27 暂停投票 | 15 承载 | 投票开始 / 结束为 `kind: 'system'`，可 `to: 'all'` |
| 28 固定团共享战役 | 15 提供 | 房间持久化；战役数据块的存取（只有 `developer` 可读写，服务程序不解析） |
| 现有单人模式 | 不影响 | 不开房间时页面行为与现在完全一致；仍可用 `python -m http.server 8080` 单机游玩 |

## Formulas

服务程序没有游戏数值，以下是它的运行阈值。

### 补发缓存
`retained(member) = min(已投递条数, REPLAY_LIMIT)`；缺口 `gap = lastDelivered − clientLastDseq`。
`gap ≤ retained` 时直接补发，否则请求快照。`REPLAY_LIMIT = 200`（与 ADR-0002 的对话窗口一致，原型实测足够）。

### 心跳
连接被判离线的最长时间 `= PING_INTERVAL + PONG_TIMEOUT = 20 s + 20 s = 40 s`。
手机切到后台常见 10–30 s 的停顿，40 s 内回来不算掉线。

### 消息大小
`MAX_MESSAGE_BYTES = 4 MiB`。依据：快照含 200 条对话、日志、地图与骰子历史，按现有存档估算 < 1 MiB，留 4 倍余量；
超过即视为异常，丢弃并告知发送者。

### 凭据强度
房间密钥、邀请码、成员令牌各 128 位随机值（`crypto.randomBytes(16)`）。房间号 6 位只用于展示，不作凭据。

## Edge Cases

| 情况 | 处理 |
|---|---|
| 守秘人用局域网地址打开页面 | 页面能打开，但看不到旧存档与密钥；开房间按钮不可用并提示"请在本机用 http://localhost:8080 打开" |
| 守秘人浏览器刷新 | 新 `epoch`；所有客户端重连时触发快照；守秘人凭令牌回到守秘人身份 |
| 守秘人断线 | 进入"等待守秘人"；玩家看到"守秘人暂时离线"；玩家请求回 `keeper_offline`；其他开发者不能顶替 |
| 守秘人浏览器丢了令牌 | 本机 8080 页面凭房间密钥加入，取回守秘人身份（发新令牌，旧令牌作废）；远程凭密钥只能成为普通开发者 |
| 两个页面同时持守秘人令牌连接 | 后连上的顶替先连上的，先前的连接收到 `system: replaced` 后断开 |
| 邀请码泄露 | 开发者重新生成邀请码；已在房间的陌生人用"移除成员"踢出（吊销令牌） |
| 热点下笔记本 IP 变化 | 玩家断线；守秘人页面从 `/__relay/info` 读新地址重新分享；玩家凭令牌重连（令牌与地址无关） |
| 端口被占用 | 启动失败并打印被占用的端口与改端口的方法（环境变量），不静默换端口——守秘人地址必须稳定 |
| 无 `openssl` | 不开 https 端口，只提供 C 档，打印说明 |
| 玩家浏览器不是安全上下文（B 档未继续、C 档） | 能玩；只提示一行"离线缓存不可用，联机游戏不受影响"；剪贴板改用兼容写法 |
| 服务程序重启 | 从 `room.json` 恢复房间；所有客户端重连；补发缓存已清空 → 全部走快照 |
| `room.json` 损坏 | 改名备份为 `room.json.bad-<时间>`，进入"无房间"，打印说明；不覆盖原文件 |
| 消息超过 4 MiB | 丢弃，回发送者 `system: too_large`；守秘人端据此缩小快照（系统 17） |
| 移除的成员用旧令牌重连 | 拒绝，`system: removed` |
| 请求路径越界（`..`、符号链接） | 404 |

## Dependencies

| 依赖 | 类型 | 说明 |
|---|---|---|
| ADR-0001 | 架构决定 | 拓扑、信任边界、信封、三档连接（本文件是它的玩法层设计） |
| ADR-0002 | 架构决定 | `dseq` 补发、快照与 `body` 的含义由系统 17 按 ADR-0002 定义 |
| Node.js ≥ 20 | 运行环境 | 内置 `crypto`、`https`；WebSocket 用 `ws` 包（与原型相同） |
| `openssl`（可选） | 运行环境 | 生成自签证书；缺失时降级为 C 档 |
| Tailscale（可选） | 运行环境 | 线上游玩；`tailscale serve` 指向 8081 |
| 原型 `prototypes/multiplayer-relay/` | 参考 | 规则已验证；**正式代码在 `server/` 重写，不复制原型** |

## Tuning Knobs

| 名称 | 默认 | 安全范围 | 作用 |
|---|---|---|---|
| `KEEPER_PORT` | 8080 | 必须与守秘人旧存档所在地址一致 | 守秘人本机 http |
| `HTTP_PORT` / `HTTPS_PORT` | 8081 / 8443 | 1024–65535 | 玩家 C 档 / A、B 档 |
| `REPLAY_LIMIT` | 200 | 50–1000 | 太小 → 短暂断线也要快照；太大 → 内存随人数线性增长 |
| `PING_INTERVAL` / `PONG_TIMEOUT` | 20 s / 20 s | 5–60 s | 太短 → 手机切后台即掉线；太长 → 离线状态显示滞后 |
| `MAX_MESSAGE_BYTES` | 4 MiB | 1–16 MiB | 快照上限 |
| `MAX_MEMBERS` | 8 | 2–12 | 超出时拒绝加入（`system: room_full`）；跑团常见 3–6 人 |

全部可由环境变量覆盖，写在 `server/config.mjs`，不在代码中硬编码。

## Acceptance Criteria

1. 启动 `server/` 后，`http://localhost:8080` 打开的游戏能读到此前用 `python -m http.server 8080` 存下的存档与 AI 设置。
2. 守秘人开房间后，页面给出的玩家链接使用局域网 / Tailscale 地址，不含 `localhost`。
3. 三档（mkcert https、自签 https、普通 http）的玩家都能加入同一房间并收到当前场景；非安全上下文只出现一行提示。
4. 服务程序拒绝：伪造 `from`、游客发 `state` / `event`、游客发给其他玩家、`to: 'all'` 的非 `system` 消息、超过 4 MiB 的消息；其他成员收不到被拒消息。
5. 断线 10 秒后重连：补发缺失消息且 `dseq` 连续；守秘人刷新后，所有成员收到新快照。
6. 守秘人断线期间，另一个开发者从局域网凭房间密钥加入得到 `developer` 而不是守秘人；守秘人凭令牌重连后恢复守秘人身份；
   守秘人丢了令牌时，从本机 8080 凭房间密钥加入取回守秘人身份。
7. 重新生成邀请码后旧码不能加入；被移除成员的令牌不能重连。
8. 服务程序重启后，已有玩家凭令牌重连成功，旧玩家链接仍有效。
9. `room.json` 中不出现明文房间密钥、邀请码或成员令牌。
10. 服务程序代码中没有任何读取 `body` 的语句（代码审查与一条测试共同保证：测试发送 `body` 为非 JSON 的二进制垃圾，投递照常）。
11. 不启动服务程序时，游戏的 `npm run ci:smoke` 与 Playwright 全部通过（单人模式不受影响）。
