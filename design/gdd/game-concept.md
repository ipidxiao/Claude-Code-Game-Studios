## Unique Hook

像 AI 叙事游戏一样自由说话，**而且** AI 守秘人被一个完整的规则引擎约束：
AI 只能通过结构化工具改变游戏状态（现状 66 个：检定、伤害、理智、线索、追逐），
"KP 协议引擎"在代码层校验它的行动，不能靠叙述改 HP/SAN 或跳过检定。

代码依据：`src/js/ai/tool_dispatch.mjs`、`src/js/ai/tool_snapshot.mjs`（工具出错整体回滚）、
`src/js/campaign/kp_execution_engine.mjs`、`src/js/data/keeper_style.mjs`（三种桌规都写明"禁止口头改 HP/SAN"）。

这一卖点与模型无关：换成任何模型，规则仍由引擎裁定。这也是支持多模型的前提。

## Core Loop

### Moment-to-Moment (30 seconds)

玩家描述行动或选择选项 → 守秘人（AI、剧本或真人）判断是否需要检定 → 骰盘出现、掷骰 →
规则引擎结算（成功档、伤害、理智）→ 守秘人叙述结果。

### Short-Term (5-15 minutes)

探索一个场景 → 获取线索（带质量档）→ 遭遇（社交 / 战斗 / 追逐 / 理智冲击）→ 进入下一个节点或地点。

### Session-Level (30-120 minutes)

完成一个剧本：从开场到按证据档分叉的结局，之后结算战后余波（伤势、疯狂、声望、警方）。

### Long-Term Progression

调查员成长（技能成长检定）、战役账本跨剧本继承、章节解锁与"推荐下一章"。

### Retention Hooks

章节地图与进度条、"可接续"徽标、结局回顾时间线、存档对比；联机后加上固定团与战役共享。

## Game Pillars

作者已确认。

### Pillar 1: 规则说了算

规则由代码执行，AI 不能绕过。规则忠实优先于叙事。
*设计测试*：如果一个功能让 AI 能不经检定改变结果，就不做。

### Pillar 2: 真相有代价

调查靠证据质量，结局按证据分叉；理智、伤势、声望的后果会延续到下一章。
*设计测试*：如果一个选择没有后果，就重新设计它。

### Pillar 3: 随时能开团

浏览器即开即玩，本地剧本无需密钥，单人也能有守秘人；真人团也能随时拉人开房间。
*设计测试*：如果一个功能增加了开局前的准备负担，需要给出理由。

### Anti-Pillars (What This Game Is NOT)

- **不是**自由沙盒聊天：AI 受规则和剧本约束。
- **不是**规则书的电子版：不收录守秘人规则书原文（覆盖率数据只存 ID / 路径 / 状态）；官方模组 PDF 只在用户本地转换、仅个人使用、不再分发。

### 第 9–11 项的规则

**9. 角色卡权限与修改日志。** 联机后，一张角色卡会被好几个人看到，需要规定谁能改什么：

| 操作 | 玩家本人 | 其他玩家 | 守秘人（开发者账号） |
|---|---|---|---|
| 查看完整角色卡 | 能 | 只看公开部分（姓名、外貌、职业） | 能 |
| 改名字、背景故事、笔记 | 能 | 不能 | 能 |
| 改 HP / SAN / 技能值 | 不能直接改，只能通过检定和规则引擎结算 | 不能 | 能手动改（例如纠正错误） |

"每次修改都记日志"指：守秘人每次**手动**改动角色卡的数值（不经过检定），都自动写一条日志，例如
"守秘人把 张三 的 SAN 从 45 改为 40"。这样手动干预有据可查，也符合支柱 1"规则说了算"。

**10. 内容安全工具（作者确认的规则）。**

- **内容限制只作用于设置它的个人**：每名玩家各自设定自己的"界限"（完全不看）和"帷幕"（一笔带过）。
  触及限制的内容，在**这名玩家**的视图里被隐藏或替换为简述；**其他玩家照常看到完整内容**。
  剧情本身不因一个人的设置而改变。
- **X 卡同样只作用于按下它的人**：按下后，当前这段内容在自己的视图里折叠，其他玩家不受影响。
- **暂停需要表决**（作者确认）：
  - 任何人可以发起暂停，全桌（含守秘人）投票。守秘人和玩家一样只有一票，**没有一票否决权**。
  - 投票时限 **10 分钟**。
  - 时限内同意票已经**大于全桌人数的一半**时，立即通过，全桌暂停。
  - 时限到了还没投票的人算**弃权**，失去本次投票权，不计入总人数；
    此时按"同意票大于已投票人数的一半"判定是否通过。
  - 例：5 人桌，10 分钟内 3 人同意即立即通过；若到时只有 4 人投票、2 同意 2 反对，则 2 不大于 2，不通过。
  - 边界：如果到时一个人都没投票，所有人都失去投票权，不再需要表决，**直接通过**（作者确认）。
- 单人模式下，玩家可以给自己设定界限与帷幕。

实现提示：因为同一段内容对不同玩家显示不同，这需要按玩家过滤后再下发，和暗骰、线索可见范围是同一套"按人过滤"机制。
另外，AI 守秘人生成叙述时需要同时产出完整版和简述版，或由前端对标记过的段落做折叠。

**11. 固定团共享战役与共享战斗面板的区别。** 两者不是一回事，作者确认两个都要做：

- **共享战斗与追逐面板**是**一场游戏之内**的事：这一场里打架、追逐时，所有人同时看到同一个先攻顺序、同一批敌人的状态。
- **固定团共享战役**是**跨越多场游戏**的事：同一批人这周跑完一个剧本，下周接着跑下一章，
  调查员的伤势、理智、声望、警方关注、已解锁章节都延续下去。现有的"战役账本"（`state/arc_ledger.mjs`）
  已经在单机上实现了跨剧本延续；固定团共享战役就是让这本账本属于整个团、所有成员都能接着用，而不是只存在一个人的浏览器里。

作者记得之前做过这两项。代码检索结果（见本节开头的表）：**单机版都已经有了**——战斗与追逐面板、战役账本、
存档导出导入都在；**跨设备共享的部分没有**——代码里没有任何网络同步（无 WebSocket、WebRTC 或服务端）。
所以这两项的工作量主要在联机同步，不在面板和账本本身。

## Target Player Profile

1. **单人玩家**：想玩克苏鲁跑团，但没有固定团或守秘人。核心玩法服务这一类（AI 守秘人为主）。
2. **真人守秘人与其玩家**：用它管理规则、骰子、角色卡并联机跑团。

`INTENT UNKNOWN`：两类用户的开发优先顺序。

## Technical Considerations

| 项 | 现状 | 目标 |
|---|---|---|
| 引擎 | 自研浏览器引擎，原生 ES 模块，Vue（vendor 内置），无打包转译 | 不变 |
| AI | 仅 DeepSeek（`src/js/ai/network.mjs`），用户自备密钥，浏览器直连 | 多模型，仍由用户自备密钥 |
| 账号 | 无 | 开发者账号与游客两种身份（控制暗骰可见性、AI 副守秘人开关） |
| 存储 | IndexedDB，存档结构第 8 版 | 本地存档保留；联机房间与固定团战役需要服务端存储 |
| 离线 | Service Worker 预缓存；本地剧本可完全离线 | 本地剧本仍可离线；AI 与联机需在线 |
| 测试 | `npm run ci:smoke`（Node 冒烟测试 + 审计 + 覆盖率门），`npm run ci` 另含 Playwright | 联机与服务端需新增测试 |

**联机带来的架构变化**：多人同步、开发者账号和固定团战役都需要一个服务程序（房间、实时消息、身份、存储），
从纯前端变为"前端 + 中转服务程序"，见 ADR-0001。暗骰数值对游客隐藏，必须由**守秘人浏览器**按身份过滤后再经服务程序下发，
不能只在前端隐藏，否则游客打开浏览器开发者工具就能看到。

**联机架构（暂行方案，2026-10-16 作者同意列为暂行；已写成 ADR-0001，状态 Proposed：`docs/architecture/adr-0001-multiplayer-relay-keeper-authority.md`）**

- **一套服务程序，线下线上通用。** 一个小型服务程序负责托管页面、房间、消息转发与固定团战役存储；
  线下和线上运行同一份代码，只是运行位置与连接方式不同。
- **守秘人浏览器是权威。** 规则引擎、AI 调用、存档仍在守秘人（开发者账号）的浏览器里运行；
  它完成结算后，为每名玩家分别生成该看到的内容（暗骰数值只发给开发者账号、内容限制按人折叠、线索按可见范围），
  服务程序只转发、不懂规则。游客的设备从一开始就收不到不该看的数据。
- **线下：热点或同一 Wi-Fi。** 守秘人用笔记本运行服务程序并开热点（或连同一 Wi-Fi），玩家用手机浏览器访问局域网地址加入。
  服务程序需自带本地证书走 https，否则 Service Worker 与"AI 接口仅限 https"的限制会失效。
  **蓝牙不可行**：浏览器网页不能充当蓝牙主机，也不能在两台浏览器之间用蓝牙传数据；手机当主机也不现实。
- **线上：Tailscale。** 守秘人笔记本照常运行同一个服务程序，玩家安装 Tailscale 客户端并接受邀请后像在局域网内一样加入；
  无需租服务器，Tailscale 还能提供 https 证书。限制：每名玩家需装客户端，守秘人电脑开着才能玩。
- **以后的升级路径：** 若需要玩家免装客户端、或守秘人离线时也能查看战役，把同一个服务程序部署到小型云服务器（如用 Caddy 自动配置 https），代码不变。
- **未采用：** 托管实时服务（Cloudflare Durable Objects、Supabase 等），因为要按其接口改写，线下模式无法复用同一套代码。

**多模型带来的要求**：现有工具调用与五段输出协议是针对 DeepSeek 调好的。
接入其他模型时，每个模型都要通过同一套工具协议契约测试（现有 `tool_schema_contract_smoke` 可作基础），
避免某个模型绕过规则引擎。

## Risks and Open Questions

### Design Risks

- 两类目标用户（单人 / 真人团）的需求可能冲突，开发优先级未定。
- 不同模型对工具协议的遵守程度不同，可能削弱支柱 1。

### Technical Risks

- 自研引擎不在本框架支持的三种引擎内，引擎专家代理与部分技能无法直接适配。
- 从纯前端转为"前端 + 服务端"，涉及身份、实时同步与服务端存储，是全新的技术领域。
- 线索板、地图、行动日志目前是全队共用一份的单机状态，改成按玩家区分可见范围会触及存档结构（第 8 版需升级）。

### Market Risks

- 自用阶段无。将来如果商用，需要先处理 Chaosium 版权与商标问题（2026-10-16 作者决定暂缓）。

### Scope Risks

- 多模型与联机辅助是两块独立的大工作。
- 开发约定已列出明确的暂缓项：深度无障碍、启动代码拆分、调查员手册 / Pulp 全目录（`src/docs/NEW_SESSION_PROMPT.md`）。

### Open Questions

1. 首批支持哪些模型？
2. 单人模式与真人团模式，哪个先做？
3. 联机方案（ADR-0001，Proposed）何时转为 Accepted？建议在最小联机原型验证通过后。

## MVP Definition

现有单人体验已远超 MVP。真人团联机辅助的最小可用版本（建议，待确认）：

1. 房间与多人同步（第 2 项）。
2. 开发者账号与游客两种身份，暗骰按身份显示（第 3 项）。
3. 共享战斗与追逐面板（第 5 项）。
4. 玩家端视图（第 1 项）。

线索分发、团务日志、共享地图、AI 副守秘人可以在此之后逐个加入。
